# 다중 클래스 향기 분류 — Plan

> AI-Studio 4클래스 제한 우회: BME688 raw 가스저항 → Python(scikit-learn) 직접 학습
> 구조: ESP32(raw 수집) → MQTT → Jetson(추론) / BSEC 4클래스는 ESP32에 그대로 유지 (하이브리드)

---

## 0. 파일 구성

| 파일 | 역할 |
|---|---|
| `parse_bmerawdata.py` | DevKit SD카드의 `.bmerawdata` → 사이클 단위 특징 CSV |
| `train_scent.py` | CSV → RandomForest 학습, 세션 분리 교차검증, confusion matrix |
| `infer_jetson.py` | Jetson 실시간 추론 노드 (MQTT raw 구독 → inference 발행) |

## 1. 왜 이 구조인가

- **raw 데이터의 정체**: 히터 10스텝(200–400°C)마다 가스저항(Ω)이 하나씩 나옴.
  가스마다 반응하는 온도가 달라서, 이 10개 값의 "모양"이 곧 냄새의 지문.
- **특징벡터 12차원**: `log10(gas) × 10스텝 + 평균 온도 + 평균 습도`
  - log10인 이유: 저항이 수만~수십만 Ω으로 널뛰어서 선형 스케일이면 모델이 큰 값에만 반응함
  - 온습도를 넣는 이유: MOX 저항이 습도에 끌려다녀서, 모델이 스스로 보상하게 특징으로 제공
- **분류기**: StandardScaler → RandomForest (기존 Jetson 프로토타입 계승).
  샘플 수천 개 규모에선 신경망보다 RF가 튜닝 없이 안정적이고, 특징 중요도로
  "어떤 히터 온도 구간이 분류에 기여했나"를 보고서 그림으로 뽑기도 좋음.

## 2. 데이터 수집 절차 (클래스당 반복)

1. 기존 로깅 펌웨어(bme68x_demo_sample, HP-301) 그대로 사용. **히터 프로파일 변경 금지** — 학습/추론 프로파일이 다르면 모델 무효.
2. 24h burn-in 완료된 DevKit 기준, 측정 전 5분 안정화.
3. 클래스 설계(예): `Air / Woody / Citrus / Floral / Mixed_WC / Odor(악취)`
4. **세션 규칙 (중요)**
   - 클래스당 **최소 3세션**, 세션당 20분 이상 (≈ 사이클 65개 × 8센서 = 520샘플)
   - 세션마다 조건을 바꿔서 수집: 소스 거리(10/30/50cm), 농도(원액 방울 수), 시간대
   - 근거: 가까이서 강한 냄새로만 학습하면 거리만 멀어져도 모델이 무너지는 실패 사례가 보고돼 있음
5. SD카드 `.bmerawdata`를 클래스별 폴더로 정리:
   ```
   data/Woody/*.bmerawdata
   data/Citrus/*.bmerawdata ...
   ```
6. Mixed 클래스는 주력 조합 1~2개만 실제로 섞어서 수집. 나머지 조합은 추론 시 확률 해석(`mixed` 플래그)으로 커버.

## 3. 학습 파이프라인 실행

```bash
# 1) 클래스별 파싱 (폴더 라벨 강제)
python3 parse_bmerawdata.py data/Woody  woody.csv  --label Woody
python3 parse_bmerawdata.py data/Citrus citrus.csv --label Citrus
# ... 클래스마다 반복

# 2) 합치기
python3 - <<'EOF'
import pandas as pd, glob
pd.concat([pd.read_csv(f) for f in glob.glob("*.csv")]).to_csv("features.csv", index=False)
EOF

# 3) 학습 + 검증
python3 train_scent.py features.csv
# → 클래스별 F1 리포트, confusion_matrix.png, scent_rf.pkl
```

### 검증 설계에서 제일 중요한 것: GroupKFold
같은 세션의 인접 사이클은 거의 복사본이라, 무작위 split 하면 train/test에
쌍둥이가 갈라져 들어가서 **점수가 가짜로 치솟음**. `train_scent.py`는
`source_file`(세션) 단위로 fold를 나눠서 "처음 보는 세션"에 대한 성능을 잰다.
→ 이 숫자가 실전 성능이고, 보고서에 쓸 숫자도 이거.

## 4. 테스트 플랜 (단계별 통과 기준)

| # | 테스트 | 방법 | 통과 기준 |
|---|---|---|---|
| T1 | 파서 검증 | 기존 Woody/Air `.bmerawdata`로 파싱 | NaN 없음 + **품질 리포트 채택률 ≥ 90%** (아래 참고) |
| T2 | BSEC 대조 | Woody vs Air 2클래스만 학습 | GroupKFold F1이 BSEC(~96%)와 동급이면 파이프라인 신뢰 확보 |
| T3 | 다중 클래스 | 4~6클래스 전체 학습 | Macro F1 ≥ 0.85, confusion matrix에서 특정 쌍 집중 오분류 없는지 |
| T4 | 일반화 | **학습에 안 쓴 새 세션** 하나를 홀드아웃 | 홀드아웃 F1이 CV 대비 -10%p 이내 |
| T5 | 실시간 | `infer_jetson.py` + ESP32 raw 발행 | 냄새 소스 교체 후 2~3사이클(≈1분) 내 라벨 전환 |
| T6 | 혼합 판정 | 두 원액 동시 노출 | `mixed: true` 뜨는지, 단독 노출 땐 false인지 |
| T7 | 강건성 | 거리 50cm/희석 조건 | 라벨 유지되는지 (무너지면 해당 조건 데이터 추가 수집 → 재학습) |

### 실패 시 디버깅 순서
1. **특정 클래스만 F1 낮음** → 그 클래스 세션 추가 수집 (불균형/다양성 부족)
2. **비슷한 향끼리 혼동** (예: Woody↔Floral) → 특징 중요도 확인 후, 히터 프로파일을 스텝 온도 간격 넓힌 커스텀으로 실험 (단, 전 클래스 재수집 필요하니 최후 수단)
3. **CV는 높은데 홀드아웃 폭락** → 세션 간 드리프트. 수집 시점 다양화 + 세션 수 늘리기
4. **실시간만 이상함** → ESP32 raw 페이로드의 step 순서/단위(Ω) 확인, 학습·추론 프로파일 일치 확인

## 5. 실시간 통합 (Phase 4 연계)

```
[ESP32] BSEC 4클래스(기존 유지) ─┐
        raw 10스텝 발행 ─────────┼─MQTT─→ [Jetson] infer_jetson.py → diffuser/{id}/inference
                                 │                └→ 제어 로직 (히스테리시스 그대로)
```
- ESP32 쪽 추가 작업: 스텝마다 `diffuser/{id}/raw`로 `{sensor, step, gas, temp, hum}` JSON 발행 (BSEC 콜백에서 raw 시그널 꺼내면 됨)
- 발향 중 센싱 시분할(발향→대기→센싱)과 히스테리시스는 기존 규칙 그대로 적용
- 보고서 프레이밍: "엣지 1차 필터(온디바이스 BSEC) + 허브 정밀 다중분류(Jetson ML)" 하이브리드 — 온디바이스 셀링포인트 유지하면서 클래스 확장을 성과로 추가

## 5.5 품질 필터 (데이터시트 3.7 / 5.3.6 근거)

파서는 각 스텝의 두 상태 비트를 확인해 불량 사이클을 버린다.

| 비트 | 0이면 무슨 뜻 | 조치 |
|---|---|---|
| `heat_stab_r` | 히터가 목표 온도에 도달하지 못함 (가열시간 부족 또는 목표온도 과다) | 저항값 신뢰 불가 → 사이클 폐기 |
| `gas_valid_r` | 실제 가스 변환이 아니라 타이밍 유지용 더미 슬롯 | 측정값이 아님 → 사이클 폐기 |

**한 스텝만 불량이어도 사이클 전체를 버린다.** 10스텝 전체가 하나의 지문이라 부분 손상 = 지문 손상.

파서 실행 시 폐기 사유별 통계가 출력된다. 해석:
- 채택률 95% 이상 → 정상
- 히터 미도달이 많음 → 히터 프로파일의 가열시간이 짧거나 목표온도가 높음. HP-301 그대로 쓰면 잘 안 나는 상황
- 더미 변환이 많음 → 정상적인 동작 (parallel mode 특성). 필터가 알아서 걸러줌
- "품질 비트 컬럼 없음" 경고 → 해당 펌웨어가 기록하지 않은 것. 필터가 자동 생략되니 그대로 진행 가능
- 채택률이 크게 떨어지면 `--no-quality-filter`로 껐을 때와 학습 F1을 비교해서 필터 효과를 확인

## 6. 주의사항

- 에탄올 희석 금지 (가스 판독 간섭) — 악취 클래스 소스 선정 시에도 알코올 베이스 피할 것
- **실록산 계열 성분(방향제·화장품에 흔함) 회피** — 금속산화물 가스센서 성능을 교란함 (datasheet 각주)
- 악취 소스는 **황 계열(VSC)이 잘 잡힘**, 순수 CO2/N2는 화학적으로 불활성이라 반응 없음
- styropyr0 등으로 raw를 직접 읽는 단계로 가면 **ADC값이 아니라 `gas_range`를 반영한 옴 변환값**을 특징으로 써야 함 (datasheet 3.7.1 공식). 레인지에 따라 스케일이 2의 거듭제곱 단위로 바뀜
- 커스텀 스캔 상한은 데이터시트 Table 5에 클래스 2~4개로 명시 → 6클래스는 BSEC 경로로 불가능. raw+Python 우회의 공식 근거로 보고서에 인용 가능
- 센서 금속 캡 접촉 금지 (오염)
- 모델/클래스 바꿀 때마다 `scent_rf.pkl`의 클래스 순서가 바뀔 수 있음 → `infer_jetson.py`는 `MODEL.classes_`를 읽으므로 자동 대응되지만, 대시보드 쪽 매핑은 재확인
- 합성 데이터 스모크 테스트는 통과 상태 (파서→학습→저장 전 구간 동작 확인). 실데이터에선 T1부터 순서대로.
